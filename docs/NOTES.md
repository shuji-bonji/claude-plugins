# Usage notes (details)

[日本語](./NOTES.ja.md) | [Back to README](../README.md)

Background and detail for each item listed under "Usage notes" in the [README](../README.md). The README says what you need to do; this document says what changed and why.

## All MCP servers

### Node.js requirement

the MCP servers start through `npx`, so your local Node.js version decides whether they start at all. `pdf-reader-mcp` / `pdf-verify-mcp` / `pdf-writer-mcp` / `pdf-spec-mcp` need **Node 20 or later**; `houki-egov-mcp` (since v0.4.0, 2026-09-07) / `houki-nta-mcp` (since v0.10.0, 2026-09-07) / `rfcxml-mcp` / `w3c-mcp` / `web-compat-mcp` / `xcomet-mcp` / `epsg-mcp` / `rxjs-mcp` need **Node 22 or later**; `ifc-core-mcp` needs **Node 22.12 or later** (`engines.node` in each repo's `package.json`). Node 20 reached end of life on 2026-04-30, and the nine servers that require Node 22 do not start on Node 20.

### Migration to MCP SDK v2

starting with the four PDF family servers on 2026-08-27, by 2026-09-07 all thirteen MCP servers moved from `@modelcontextprotocol/sdk` (v1) to `@modelcontextprotocol/server@^2.0.0` (`houki-egov-mcp` in v0.4.0 and `houki-nta-mcp` in v0.10.0, both on 2026-09-07; the latter closes [claude-plugins#4](https://github.com/shuji-bonji/claude-plugins/issues/4)). Two changes reach callers of the eleven servers that use the SDK's `registerTool`. (1) **`inputSchema` in `tools/list` now declares `$schema` as JSON Schema 2020-12** (it was draft-07). (2) **An argument whose type does not match is rejected by the SDK before the handler runs and comes back as a tool result with `isError: true` (`Input validation error: ...`)** — until now each server validated on its own and the JSON it returned differed. Whether an argument the schema does not declare is rejected or silently dropped still differs per server (the four PDF family servers reject it — see the next paragraph). `houki-egov-mcp` (from v0.5.3) and `houki-nta-mcp` (from v0.10.0) are the exceptions on both points: they keep the SDK's low-level `Server` so that their error JSON stays on the houki-hub family contract, so their `inputSchema` carries no `$schema` (plain JSON Schema, unchanged from before), and a type, required-field or enum violation is rejected before the handler runs as `{ "code": "INVALID_ARGUMENT", "detail": { "issues": [...] } }` with `isError: true` rather than as `Input validation error: ...`; an argument the schema does not declare is passed through. `houki-nta-mcp` v0.10.0 also changed two things that v0.9.5 did differently: a call naming a tool the server does not have now comes back as `{ "code": "UNKNOWN_TOOL" }` with `isError: true` (it used to be `{ "error": "Unknown tool: ..." }`), and a tool result that is a family error object (`TSUTATSU_NOT_FOUND`, `ARTICLE_NOT_FOUND`, ...) now carries `isError: true` (it used to come back as a plain result). As long as you pass tool names and arguments as declared, nothing changes for `npx` users. Some servers raised their Node requirement in the same release — see the Node.js requirement above. w3c-mcp v0.2.0 removed `get_spec_dependencies`, deprecated since 0.1.9 (upstream `web-specs` never exposed dependency data, so it only ever returned empty arrays; use `get_w3c_spec`).

### The four PDF family MCP servers (the 2026-08-27 releases)

`pdf-spec-mcp` v0.6.0, `pdf-reader-mcp` v0.13.0, `pdf-verify-mcp` v0.18.0 and `pdf-writer-mcp` v0.21.0 neither gain nor lose a tool, and no tool's output changed — but **three things reach callers**. (1) **An argument the input schema does not declare is now rejected**; until now it was silently dropped and the call ran. (2) **A call naming a tool the server does not have comes back as a JSON-RPC error**, where it used to be a tool result with `isError: true`; a client that only reads `isError` will not see it, and `await client.callTool(...)` throws instead of resolving. (3) `inputSchema` now declares `$schema` as JSON Schema 2020-12, and `pdf-writer-mcp`'s `add_bookmarks` moves its `$ref` target from `#/definitions/` to `#/$defs/`. `pdf-reader-mcp` also **requires Node 20 or later** now (v0.12.0 still ran on 18). Using them through the Skills (pdf-trust / pdf-publish / pdf-read) is unaffected — every argument those Skills pass was checked against the declared schemas.

## pdf-reader-mcp

### v0.14.0 — the shape of what the text-returning tools return

**`pdf-reader-mcp` v0.14.0 changes the shape of what the text-returning tools return.** Taking the characters off a page and observing whether those characters have a route to Unicode (ISO 32000-2 §9.10.1) are separate readings that fail separately, so every such tool now carries `scope` saying which of them were done, and **a field whose reading did not happen is `null` — never `0`, `false` or `""`**. `read_text` and `read_url` return `{ scope, pages }` where they returned a bare array of pages. Two defects are fixed with it: `read_url` used to return an error for **every** input (the fetched bytes were handed to two readers, and the first took them away), and `render_page` could stop the server for good on a page whose tiling pattern asks for an astronomical number of tiles — it now runs off the main thread with a 20-second budget per page. Through the Skills this is handled for you: use `pdf-read` **v0.2.0+** and `pdf-publish` **v0.7.0+**, which read `scope`. On the older Skills against a 0.14.0 server, the stop for a password-protected document does not fire.

### v0.15.0 — what `inspect_structure` returns

**`pdf-reader-mcp` v0.15.0 changes what `inspect_structure` returns.** pdf-lib is gone; every reading now goes through [`@normativepdf/recover`](https://www.npmjs.com/package/@normativepdf/recover). `objectStats.byType` and `catalog[].type` used to carry pdf-lib's class names (`PDFCatalog`, `PDFPageTree`, `PDFRawStream`, `PDFNumber`, …); they now carry the COS types of ISO 32000-2 §7.3 (`dict`, `stream`, `array`, `name`, `string`, `integer`, `real`, `boolean`, `null`, `ref`). The dictionary's `/Type` (`Catalog`, `Pages`, `Page`, `Font`, …) moves to a separate field, `objectStats.byDocType`; objects the cross-reference table does not name are no longer counted, and objects it names but that could not be read appear in `objectStats.unreadable`. Encrypted documents whose key can be derived from the empty user password are now read, and where the key cannot be derived `inspect_signatures` names the reason instead of reporting "0 signature fields". A caller that reads the values of `objectStats.byType` has to be updated.

## pdf-verify-mcp (prerequisite of pdf-trust)

### v0.14.0 and earlier — every document timestamp came back INDETERMINATE

Its prerequisite `pdf-verify-mcp` had a defect in **v0.14.0 and earlier** where every document timestamp (ETSI.RFC3161) came back **INDETERMINATE** (**fixed in v0.14.2**; confirmed against three independent specimen families — pyHanko, esig/dss, and the Japanese official gazette). Run long-term-preservation audits (B-LTA, denchōhō) on v0.14.2 or later.

### v0.14.2 and earlier — an incomplete revision chain reported as complete

In `pdf-verify-mcp` **v0.14.2 and earlier**, a `/Prev` link that could not be followed was read as "there is no previous cross-reference section", so the revision chain was reported as complete when it was not — a specimen with 8 revisions and 5 signatures came back as having one (**fixed in v0.15.0**). Any audit whose report promises the _full_ revision history — the `legal` and `medical` profiles, and any contract dispute over whether the body text was altered after signing — must be run on **v0.15.0 or later**. On earlier versions the shortened list cannot be distinguished from a document that was never changed.

### v0.15.1 to v0.16.0 — what a report can claim

three `pdf-verify-mcp` changes affect wording rather than verdicts. **v0.15.1** records which veraPDF build decided a conformance result (`authoritativeValidation.version`) — a rule count such as "146 / 146" is only comparable across runs of the same build, so a report from an earlier version cannot say what produced its numbers. **v0.15.2** corrects the `verify_integrity` description: a returned `revisions` list can be a part of the history rather than all of it. **v0.16.0** makes that a field, `revisionChain: { status, missing }` — before it the only signal was English prose in `notes`, so the skill decided whether it could promise a _full_ revision history by matching sentences. Only `status: 'complete'` lets a report say "this change does not appear in the list, so it was not made"; with a cut chain the one surviving revision is reported as the original, and every machine-readable field then reads as "nothing was appended". **pdf-trust v0.6.0 and later read the field**, and keeps the prose fallback for 0.15.x. None of the three is a defect in the verdicts of earlier versions; all three change what a report can honestly claim.

### v0.20.0 to v0.21.0 — output shape

in `pdf-verify-mcp` **v0.21.0** the JSON of `verify_signatures` and `detect_pades_level` changed its top level from an array to an object (`[ {...} ]` → `{ scope, signatures: [ {...} ] }` / `{ scope, levels: [ {...} ] }`; not one key inside the list changed). A caller that read the array directly has to go through `.signatures` / `.levels`. The reason is `scope`: in a document whose cross-reference table was rebuilt (`scope.reconstructed: true`), a signature the rebuild did not reach is absent from the list, so the range that was read has to be visible next to the list. v0.20.0 also split the `code` of a refusal that names a clause out of `INTERNAL_ERROR` into `PARSE_FAILED`. **pdf-trust v0.8.0** reads `scope` before deciding (Phase 1.5) and does not file `PARSE_FAILED` under "checks not performed"; its README recommends **pdf-verify-mcp v0.21.0 or later**.

## pdf-writer-mcp (prerequisite of pdf-publish)

Its prerequisite `pdf-writer-mcp` is also in the marketplace (see the table above for the version). PDF/A-3b container support (`ensure_pdfa`) landed in **v0.15.0**; **PDF/A-4 and PDF/A-4f, plus PDF 2.0 output, landed in v0.16.0** (a document carrying a CSV or JSON attachment has to be declared `pdfa-4f`, not `pdfa-4`). Since **v0.17.0** `ensure_pdfa` also reports `declarationRisks` — a claim that is already known to fail validation (today: fonts that are not embedded) is named, instead of being left inside the prose warning. Note that v0.14.0 and earlier have a defect where `_` in `snake_case` is silently dropped during Markdown generation ([B-17](https://github.com/shuji-bonji/pdf-writer-mcp/blob/main/docs/TASKS.md) — **fixed in v0.14.1**). If you are pinned to an older release, check the output of any technical document that contains function names. v0.18.0 and earlier also have a defect where `preserveSignatures: true` writes a damaged file when the input does not begin with `%PDF-` at byte 0 — legal per ISO 32000-2 §7.5.2, and produced by any tool that prepends bytes ([B-22](https://github.com/shuji-bonji/pdf-writer-mcp/blob/main/docs/TASKS.md) — **fixed in v0.19.0**).

## pdf-spec-mcp

You must supply the ISO 32000 specification PDFs yourself and point the `PDF_SPEC_DIR` environment variable at their location. Since **v0.5.0** the search index and the full requirements scan are cached on disk after their first build (`${XDG_CACHE_HOME:-~/.cache}/pdf-spec-mcp`, about 18 MB for the whole corpus; `PDF_SPEC_CACHE_DIR` moves it, `PDF_SPEC_CACHE=off` disables it), so a server process started for a new session answers `search_spec` in well under a second instead of rebuilding for 6–14 s. `npx -y @shuji-bonji/pdf-spec-mcp@latest --build-cache` warms every spec up front. The cache is derived from your own copy of the PDFs and stays on your machine.

## xcomet-mcp

Requires a local Python environment with xCOMET installed. `XCOMET_PYTHON_PATH` is **optional** as of **v0.6.3** — set it only when you use a venv or a non-default interpreter; otherwise the server auto-detects one. See the [repo README](https://github.com/shuji-bonji/xcomet-mcp-server) for details.
